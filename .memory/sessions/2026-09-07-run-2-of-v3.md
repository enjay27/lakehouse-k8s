`diff_reports`' DEFAULT rather than in a set the caller has to remember, because the caller
forgot.

**The rest is the notebook's own untagged traffic.** `setup_fixture`, `authorize_on_fixture`,
`provision_run_principal` and `teardown_fixture` all issue real calls inside the merged
windows and none of them is in `ALL_CALLS`, so the oracle cannot predict them. That is
exactly what the 5 extra rows are (`probe_ns2`, `_shared` + grants, the provisioned
principals and roles) and why all 21 deltas run one way. **Nothing in this run points at the
pipeline losing a record.**

## A real skipped window, and a wrong turn about it

The gap check fired truthfully for the first time: one gap, `00:35:30Z -> 00:37:30Z`, three
windows with no report at all, ~48 minutes before the run's own (contiguous) windows.

I first told Kade the gaps in his ad-hoc query were an artifact of a 50-row cap. Most were —
the result was unordered and capped at exactly 50 of ~84 windows — **but this one is real**,
and the notebook's own check found it independently at `limit=5000`, filtered by hostname and
`window_seconds`. Kade then offered "I ran cell by cell, so it may cause time diff", which is
also not it: the report tick comes from Fluent Bit's own `dummy` INPUT, idle windows emit
summaries all night, and a slow notebook spans more windows rather than skipping any.

What it leaves is a distinction the notebook cannot make, because it only sees VictoriaLogs:
**never emitted** (a ~90s stall of the shipper process) versus **emitted and lost in transit**
(the HTTP output failing — a flapping port-forward fits a hand-paced session well). The
Fluent Bit output metrics settle it and are still readable: cumulative counters, pod
unrestarted since 2026-09-04.
