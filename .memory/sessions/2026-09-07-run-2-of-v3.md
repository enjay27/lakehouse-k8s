## The drop counter has never worked, and nobody could have known

```
fluent-bit drop_records    7,154,980,971,680 (before)
fluent-bit drop delta      52000.0
```

7.15 trillion is not a record count. It is almost exactly **four times the epoch in
milliseconds**, so `parse_fluentbit_metrics` is handing `drop_records_total` a
timestamp-shaped field from about four plugins. The honest figure should have been of order
90 (counted-only access records) plus ~30 swallowed ticks.

**This was invisible for two runs because the port-forward was down and the number came back
`unknown`** — which reads as "not measured" and is therefore harmless. The moment it came back
as a number it was quotable, and it was wrong. The guard now refuses to print any total at or
above 10^9 and prints the per-plugin breakdown instead, so the next reading names the plugin
rather than producing a silent sum. **The parser itself is still unfixed**: it needs the real
shape of that endpoint, which is not reachable from a Cowork shell.

## And a ratio that could not be read literally

not in `ALL_CALLS`) while the denominator counted the calls. Correlation is the statistic the
entire per-call matrix rests on. `lc.correlation_stats` now reports recovered-of-carried and

# Both open questions closed, from two commands on Kade's machine

## Stack traces: there are none to lose

```
kubectl -n datahub-hynix exec deploy/benchmarks-polaris -- grep -c stackTrace \
  /deployments/logs/polaris.log
0
```

Zero in the SOURCE FILE. So `0 of 5` was never about the pipeline: **Polaris does not write
stack traces into its log at all.** No retention policy could have preserved them, and no
change to Fluent Bit will produce them. It is a Quarkus JSON-encoder setting, and until it is
changed every 500 in this cluster is undiagnosable from logs alone — what arrives is one line,
`Unhandled exception returning INTERNAL_SERVER_ERROR`, with no exception class, no message and
no cause.

Worth noticing how close this came to being recorded backwards. `0 of 5` in a results document
reads as "the pipeline drops them", and that is the sentence a reader would have quoted six
months out. The notebook printed the check that distinguishes them next to the number, which is
the only reason the right answer was one command away.

## The drop counter: a trailing timestamp, taken as the value

The metrics document settled it:

```json
"filter": {"polaris_noise_filter": {"drop_records": 1943, "add_records": 534,
                                    "records": 21817, "drop_bytes": 447813}}
```

1,943, not 7,154,980,971,680. The JSON path parses correctly — but `fluentbit_metrics` tries
`/api/v1/metrics/prometheus` FIRST, and Fluent Bit's Prometheus encoder appends an optional
**millisecond timestamp** after the sample value:

```
fluentbit_filter_drop_records_total{name="polaris_noise_filter"} 1943 1788745242920
```

`rpartition(" ")` took the timestamp. Four filters × epoch-ms = 7,154,980,971,680, which is
exactly what was printed. The same bug mangled the plugin name into
`polaris_noise_filter"} 1943`, which nobody saw because only the sum was ever displayed —
**the per-plugin breakdown added as a guard last commit would have exposed it on sight.**

Parsed correctly it reconciles all the way down: the noise filter's
`records 21,817 = 20,322 tailed + 1,495 ticks`, exactly; and 1,943 drops is about 1,246
non-boundary ticks swallowed plus the counted-only access records of every run so far.

## And the missing windows, answered by the same document

The HTTP output reports `errors 0, retries 0, retries_failed 0, dropped_records 0` cumulatively
since the pod started on 2026-09-04. **Nothing the filter emitted was ever lost in transit**, so
the three missing windows were never emitted — and the tick counter says why.

`polaris_report_tick` has produced **1,495 records** against ~65.5 hours of pod uptime. At
`Interval_Sec 5` that should be ~47,000. It has ticked for about **3%** of its own uptime, and
the gate's independent `report records (24h) = 333` agrees.

**The OrbStack VM is suspended with the MacBook.** The container's timer does not fire, windows
never open, and a window that never opened cannot be reported. That is the whole of the
skipped-window finding, and it retires the more alarming reading: it is not a Fluent Bit stall
and not a Lua fault. Three consequences worth keeping: a gap is EXPECTED here after any sleep;
records processed around a suspend are counted into no report, which is the startup blind
spot's cousin; and **no measurement over the report stream that spans a sleep can be read as
elapsed time** — 333 reports in 24h is 2.8 hours of windows, not a rate.

# Retraction: the stack traces were there all along

Kade pasted the exception payload from a stored document: a JSON array of
`{class, method, line}` frames, 60 of them, `IcebergCatalogHandler.createNamespace` at the top.

**So "Polaris writes no stack traces" was wrong.** This build emits Quarkus's *structured*
exception output, not a `stackTrace` string — which is why `grep -c stackTrace` returned 0, and
why the notebook's `"exception" in record` returned 0 of 5 once a store had flattened the object
into `exception.frames` / `exception.exceptionType`. **Two checks looking for the same wrong
name, agreeing with each other, and read as corroboration.** One error twice.

The bitter part: the previous entry in this file congratulates the harness for printing "the
distinguishing check beside the number", and the distinguishing check was a grep for the same
wrong name. A confirmation that shares an assumption with the thing it confirms is not a
confirmation, and neither of us noticed because both halves said zero.

**Fixed the only way that generalises:** `lc.exception_fields` returns the field NAMES it finds
rather than a boolean, across the shapes this pipeline can produce — a nested or flattened
object under any of `exception` / `stacktrace` / `stack_trace` / `throwable` / `frames`, and a
`formatted` trace sitting as text inside another field's value. A check that can only answer yes
or no cannot distinguish "absent" from "looked for the wrong name", and those two have opposite
remedies: one is a logging change in another repo, the other is one line here.

**Still open and now correctly stated:** whether the payload is in
`/deployments/logs/polaris.log` (as opposed to container stdout, which the DaemonSet ships to
OpenSearch by a different path), and whether it survives into VictoriaLogs. Only the second is a
statement about the pipeline this notebook tests. The `local-k8s` handoff has a retraction at
its section 2 so no session acts on the config recommendation.
