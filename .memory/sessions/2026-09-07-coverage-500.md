# 2026-09-07 — Coverage: 500 error

**Task, as given:** *"Read CLAUDE.md, MEMORY.md and log-coverage/PLAN-log-coverage-v3.md, and
then make new Coverage: 500 Error. Currently, there are no 500 errors in real stored logs."*

Written for someone starting cold. The wrong turns are in here because they are the part most
likely to be repeated.

## What was actually wrong

"No 500 errors in real stored logs" is a symptom with two candidate causes and they have
opposite remedies: the pipeline drops them, or nothing provokes them. **It was the second, and
it had been reported as the first.**

`neg.500_null_pointer` drove `create_catalog_no_endpoint`, which builds a catalog whose
`storageConfigInfo` omits `endpointInternal` — and sets `endpoint`. **This build falls back to
`endpoint` when `endpointInternal` is absent**, so the NullPointerException the probe is named
for cannot happen and has not happened since at least 2026-09-04. The probe returned **200 for
three consecutive runs**.

Nothing caught it, and the reason is worth more than the bug:

- nothing asserted on the probe's status — it was driven, its status was recorded in the matrix,
  and no cell compared it to 500;
- the results document rendered **"0 of 0 WARN/ERROR records carried an exception object"**,
  which reads exactly like a measurement of the pipeline. `0 of 0` is a measurement of the
  *probe*. Run 2 shipped that line; run 3 shipped `0 of 5`, and the 5 were **accidental**.

The accidental ones are the PG-HA read-after-write failures on `iceberg.create_namespace` /
`iceberg.create_view`. Those are **writes that committed** — on 2026-09-01 `load_view`,
`head_view`, `rename_view` and `drop_view` all answered 2xx after one, which is impossible
unless the create landed. So they say nothing about the unhandled-exception path in either
direction, and counting them as ERROR-path coverage claims a measurement nobody took.

## The thing I got right by reading the source rather than the plan

**A 500 is two records.** I nearly wrote a section that checked one.

| half | logger | rule | disposition |
|---|---|---|---|
| access-log line, `http_status 500` | `io.quarkus.http.access-log` | 3 | kept **and** counted — every access-log record is counted before any keep/drop decision, so it moves `access_seen`, `errors_kept` and the row's `errors` |
| application ERROR line | the handler's own logger | 2 → 1 | kept, and counted into **nothing** |

Only the second half carries the trace, and only under its **flattened** name
`exception.frames`. So a check on the summary counters can pass while the half carrying the
stack trace is missing, and a check on the ERROR record can pass while the access line was
dropped. §11c checks them separately and joins them on `mdc.requestId`.

## What was built

- `lc.provokers_500` — a **ladder** of three API-only, reversible, self-cleaning rungs, tried
  cheapest first: both storage endpoints at a dead port; a bucket that does not exist; a stale
  `entityVersion` PUT. `lc.drive_500` stops at the first that really returns >= 500.
- `lc.classify_500s` — `deliberate` / `read_after_write` / `unknown`, from the LABEL. A 500 body
  cannot say whether the write committed, and the PG-HA signature is exactly a 500 whose write
  did. Anything unrecognised is `unknown`, never folded into either bucket.
- `lc.error_record_pair` — the two halves, with the exception field NAMES found.
- `lc.check_500_window` — the `errors_5xx` assertions, `ok=None` meaning VOID.
- `vlogs.exception_term` / `VLogs.exception_records` — ask for the payload by **every** name it
  can have. `with_exception` is left exactly as it was, so a run comparing the two can see the
  difference rather than inherit the fix silently.
- `VLogs.field_is_numeric` — `type_int_key`, per field. A counter stored as the string `"3.0"`
  renders in every count and matches no range filter. This pipeline has now produced that shape
  of failure twice (the Prometheus timestamp; `type_int_key` itself).
- Notebook **§5c** (drive) and **§11c** (assert); `neg.500_null_pointer` **retired** with a note
  saying what it used to do and when it stopped, rendered into the results document as
  *Retired probes*.

## Three decisions, and why

1. **A ladder, not a repointed probe.** A single provocation is exactly what just failed. The
   ladder also records what each rung returned, so the next session can see a rung go stale
   instead of inheriting a silent 200.
2. **`purge=False` on every cleanup.** `purgeRequested=true` asks Polaris to delete the
   underlying files — i.e. to talk to the storage endpoint rung 1 just pointed at a dead port.
   That either hangs or provokes a second, untagged 500 during teardown. The old `NPE_CAT`
   cleanup used `purge=True`.
3. **`127.0.0.1:1`, not a routable-but-dead host.** It refuses instantly. A host that hangs would
   leave **no access-log line at all** — the one failure this pipeline is structurally blind to —
   and the probe would then be measuring the blind spot instead of the ERROR path.

## What is NOT done, deliberately

- **No rung has ever been observed to fire.** All three are `[assumed]`. I cannot reach the
  cluster from Cowork — no kubectl, no port-forward, no route — so 500 coverage is *built* and
  not *demonstrated*. If every rung returns 2xx the honest options are in
  `PLAN-log-coverage-schema-v2` §4, and "accept the accidental 500s" requires saying in the
  results that ERROR-path coverage is opportunistic and not repeatable.
- **The oracle is still schema v1** while the deployed filter is v2. `check_500_window` is
  written to report VOID rather than pass on a window with no error split, but the migration
  (that plan's §1, starting at 1.1) is a separate task and is named in `active-issues.md` so
  nobody asserts a v2 field through a v1 oracle by accident.
- **`error-cases/09_500_null_pointer` is still stale.** Its assertion would fail for the same
  reason. Left alone rather than half-fixed in a commit about something else.

## Gate

`black` + `isort` on the three changed modules; **705 passed / 1 failed**, the failure being the
pre-existing `test_privilege_scan` renderer drift `MEMORY.md` already records. Run under
`uv run --no-project --with pytest ...`: the repo `.venv` is a **macOS** build and the Cowork
bridge sees Linux, so `.venv/bin/python` cannot execute at all. Black 26 also reflowed about
twenty pre-existing lines in the files it touched — cosmetic, and in the same commit rather than
hidden in a later one.

# Part 2 — the gate aborted, and the oracle was a schema version behind

Kade ran the notebook and cell 0b failed with eight "unexpected fields", one "missing field" and
`schema_version '2'`, repeated per stored row. **Every one of those rows was correct.** The
filter had shipped schema v2; `log_coverage.SCHEMA_VERSION` was 1.

## What I did differently, and it is the reason this went quickly

**I read the deployed `build_report`, not the error message.** Requesting access to
`local-k8s/logging` took one call and settled every field, its type, and — more importantly —
its *semantics*, which the error text cannot carry:

- the summary's `errors_4xx` / `errors_5xx` / `auth_denied` / `bytes_total` are summed **over
  resources only**, because the two margins are equal by the invariant and doing both would
  double-count. So on oracle rows those identities hold by construction, and on **stored** rows
  they are a transport check across Fluent Bit's array split. That distinction is the difference
  between a test that can go red and one that cannot;
- `distinct_resources` counts rows with `requests > 0`, **not** rows emitted, with `carried_rows`
  beside it — v1 conflated them, which is why an idle window reported two distinct resources;
- a `nil` status increments `errors` and **neither** half of the split, deliberately, so that
  "client errors" does not absorb the pipeline's own failures. That is why the invariant is
  `errors_4xx + errors_5xx <= errors` and not an equality.

Guessing any of those three from the truncated traceback would have produced a green test suite
asserting the wrong thing.

## The bug worth remembering

`merge_windows` summed a **hardcoded tuple**. Under v2 it would have added `errors` and silently
not added `errors_4xx` — *in the same row*. No exception, a plausible number. That is the third
instance of this exact shape in this pipeline: `type_int_key` on the shipper, the Prometheus
parser reading a trailing millisecond timestamp as its value, and now this. The fix is not a
longer list; it is deriving the list from the data and writing down, per exclusion, why that
field must not be added.

## And a tooling change with more leverage than the code

**The oracle tests now run from Cowork.** They had always skipped here for want of a Lua binary
and `fb-values.yaml`. Installing `lua5.4` in the cloud container and pointing `FB_VALUES_PATH` at
the staged values file runs all 115 **against the filter that actually ships** — characterization
tests included. The first run immediately found three bugs: two of mine (`report_windows` returns
`predict()`-shaped dicts, not bare verdict strings — I had written `verdicts == ["keep"]`) and one
latent (`merge_windows` raising `KeyError: 'access_kept'` from a format string when a summary row
lacked a counter, i.e. a schema question surfacing as a crash three functions from its cause).

Before this, "37 skipped" was the normal result from this side and nobody could tell a skip from
a pass.

## What the plan got wrong, recorded because it is instructive

**1.6 expected the characterization tests to go red. They did not, and should not have.** v2
changed the report *schema*; the keep/drop *policy* is untouched, so the three characterization
tests had nothing to say about it. A plan that predicts a red test and gets green invites the
next reader to assume the test is not wired up — it is, and it passed 115/115.

## Still open

The 500 ladder **still has never fired.** Part 1's caveat is unchanged: all three rungs are
`[assumed]`, and the first real answer comes from a run that reaches §5c — which the gate was
blocking, and no longer is.

# Part 3 — Kade's case: wrong MinIO host or auth

**The question:** could a wrong MinIO auth or host at catalog create provoke a 500, or only a
400 / an INFO line? It splits three ways and two of the answers were already in the repo.

- **Not at catalog create.** Polaris does not validate storage config on `POST /catalogs`
  (`error-cases/23`: *"Catalog create succeeds — Polaris does not verify bucket"*) — it returns
  201, and the failure surfaces at the first operation that touches storage. Every rung
  therefore creates the catalog, then creates a **table**.
- **Wrong host: yes, 500 is the expected shape**, and the repo had already measured the family:
  *"clones have no MinIO objects and anything vending credentials 500s against one"*
  (`sessions/2026-08-31-full-get-surface.md`). **Added as rung 2, `unresolvable_host`** — a
  typo'd in-cluster service name, which is the mistake people actually make. Kept SEPARATE from
  rung 1 rather than swapped in for it: DNS resolution and TCP connect are different layers and
  the S3 client may handle them in different code paths, so one can 500 where the other does
  not, and a ladder testing only one would report NOT PROVOKED with the answer in the next rung.
  `.invalid` (RFC 2606) because a plausible-but-wrong name risks resolving to something real.
- **Wrong auth: not reachable from a client at all, so NOT a rung.** `storageConfigInfo` carries
  no credentials; Polaris uses static server-side ones shared by every catalog
  (`purge/doc-purge-minio-issue-briefing.md`: *"falls back to the static MinIO creds"*). Making
  them wrong is a `local-k8s` deployment change that breaks every catalog and needs a Polaris
  restart — and a restart mid-run voids the run. Recorded in the scenario document's
  *not in the ladder* table so the next person does not re-derive it.

## The part of his question that changed the design

**"or just 400 or INFO?"** — that is the handled-versus-unhandled distinction, and §11c could not
express it. Polaris can CATCH a storage failure, map it to a 500 and log it **without** attaching
the throwable; the old check asked only "did a trace arrive?" and would have reported that
identically to a pipeline that dropped one. **Opposite remedies: change the probe, or fix the
shipper.**

So `lc.trace_verdict` now returns three:

| verdict | seen | means |
|---|---|---|
| `unhandled` | application line **with** a throwable | the trace survived; what §5c exists to show |
| `handled` | application line(s), **no** throwable | nothing was lost — there was never a trace. A fact about the PROVOCATION |
| `absent` | **no** application line | rule 2 forbids it. **The only one that accuses the pipeline** |

A5 is now VOID (not FAIL) when every 500 was handled, and says so in words. The level is
deliberately not the question — rule 2 keeps a non-access-log record whatever its level, so a
WARN line carrying a throwable is `unhandled`.

**Deliverable:** `log-coverage/doc-500-coverage-scenario.md` — the scenario in full, written to
be checked before the run rather than after it.

# Part 4 — the run, and what it closed

Run `1788759324`. Cells 0-14 clean, gate green (`schema_version (deployed / ours) 2 / 2`).

## The answer is NOT PROVOKED, and that is a result

| rung | measured |
|---|---|
| `black_hole_endpoint` | **422** x3 |
| `unresolvable_host` | **422** x3 |
| `nonexistent_bucket` | **400** x3 |
| `stale_entity_version` | **409** x3 |

`org.apache.polaris.service.exception.IcebergExceptionMapper` logged 50 records. Polaris CATCHES
the storage failure and maps it, so **a broken storage configuration is a CLIENT error on this
build** and never reaches `errors_5xx`. Kade's question is answered directly: a wrong MinIO host
is a **422**, refused or unresolvable alike.

The rungs stay in the ladder. They are cheap, they document four closed routes so nobody
re-derives them, and a build change that started returning 500 would surface as a rung firing
rather than as a silent gap.

**The contract is what made this readable.** §5c printed NOT PROVOKED; the results document says
so; question 3's payload is explicitly attributed to the ACCIDENTAL records. Compare the three
runs where a probe returning 200 rendered as "0 of 0 records carried an exception object" and
was quoted as a property of the pipeline.

## Two defects the run exposed, both mine

**1. "Pure-500 burst" assumes the ladder fires.** It did not, so twelve 4xx landed in the very
window the checks call pure, and a hardcoded `driven_4xx=0` printed
`a 500 does not increment errors_4xx: errors_4xx=13, driven 4xx=0`. **The harness reporting its
own traffic as a fault in the filter** — the exact failure mode this section was written
against, in a new place. `lc.driven_status_mix` now counts what was actually driven.

**2. The summary has no `errors` field.** It has `errors_kept`, which counts access records the
error rule kept, not error requests. `summary.get("errors")` returned 0 and the check printed
`13 + 1 <= 0  FAIL` against a window whose numbers reconciled perfectly (the margin two lines
below read `14 vs 14`). Now taken from the resource margin, which is what `build_report` sums
the split from in the first place.

Both are the same lesson as 1.1: **a field name assumed rather than read off the source.** I
read `build_report` for the field SETS and did not re-read it for this check.

## What the run gave for free

- **Stack traces are richer than anything recorded here: 7 of 7, under FOUR names** --
  `exception.exceptionType`, `exception.frames`, `exception.message`, `exception.refId`. Earlier
  entries only ever named `frames`.
- **48 records in the run carried an exception field**, so traces accompany HANDLED 4xx too, not
  only unhandled 500s. That is a bigger statement about the pipeline than the 500 path alone.
- **v2 is validated against real stored data**, not only against the oracle: three windows, all
  invariants green per-window and merged, zero-carry 19/19, decay clean, one summary per
  (host, window) across 152 consecutive windows with no gaps, `errors_5xx` numeric.

## Still open

**No known way to provoke an unhandled exception on this build.** Storage misconfiguration is
exhausted. The `handled` / `unhandled` verdict has therefore never been exercised on a driven
500 -- it exists, it is tested at the unit level, and it has never had a real record to judge.

# Part 5 — closing the open issues, and the handoff

## "154 of 157" was the policy working

The three probes named as not recovered were `probe.read the table` #2 and #3 and
`probe.write the table`. Every one: `expected=drop, disposition=counted, stored=0,
app_lines=0`. Rule 6 dropped their access-log line **on purpose**, and they emitted no
application line either — so there was nothing to find.

Why only #2 and #3: **the first `load_table` emitted one application line and the warm repeats
emitted none.** Cache warmth decides. The matrix's own `discrepancy` column was blank for all
three, i.e. the matrix knew they were fine and the correlation ratio did not.

Fixed by splitting the ratio: `lc.correlation_by_disposition` reports KEPT and COUNTED apart.
**Only KEPT is an assertion.** A counted call is findable only incidentally.

## The finding underneath it, which is worth more than the fix

v3's cost has been written down all along as *"successful reads leave no individual record; they
are counted, not lost"*. That is too weak. A counted call whose application logging is also
silent leaves **nothing at all** — and what decides that is cache state, not policy. So the
honest sentence is **"a warm repeat of a successful read is invisible end to end"**, and
`lc.invisible_calls` now counts them into question 5 so nobody has to infer it.

## The blocker, named rather than left open

Nothing provokes an unhandled exception on this build. Four rungs, all 4xx. The best untried
candidate is **inducing PG replica lag deliberately** — pause WAL replay on a standby, drive
`create_namespace`, resume — which turns the one 500 signature this cluster actually produces
into a probe instead of an accident. It needs psql, so it belongs to `local-k8s`.

If that fails, the close is explicit: ERROR-path coverage is *opportunistic and not repeatable*,
written into the scenario document and the results, rather than a question left hanging for a
fourth run.

## Handoff

`log-coverage/HANDOFF-500-coverage-2026-09-07.md`, written to be read cold: the four commits,
what is settled (with the measured statuses), the three open items in priority order, what comes
back from the `local-k8s` session, the next actions in order, the gotchas that already cost time,
and — new this session — **how to run the oracle tests from Cowork at all**, which is what turned
"37 skipped" into 120 passed.
