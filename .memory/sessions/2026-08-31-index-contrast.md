# 2026-08-31 — the EXPLAIN sweep read, and two faults in the reader

Second session of the day. The first banked six captures; this one read them.
Deliverable: `diagnostics/api-sql-profile/doc-grant-index-contrast-20260831.md`.

## The finding

At 60,784 `grant_records`, the grantee lookup takes a **Seq Scan of 572 pages,
discarding 60,783 rows to return 1**, with the index absent; an **Index Scan of
3 pages discarding none** with it present. Identical across three independently
seeded fixtures. 190x fewer pages for the same answer.

`shared_read` is 0 everywhere — the table is 4.5 MiB and fully cached — so this
is CPU and buffer-pin cost, not I/O, and the ratio is a page-access ratio, not a
latency ratio. Say so whenever it is quoted.

The control is in the same table: the securable-side lookup is already covered
by `grant_records_pkey`, takes an Index Only Scan at 3-5 buffers, and does not
move when the index is toggled. Same table, same pass — so nothing ambient
explains the contrast.

Denial path: **6,000 refusals, exactly 7 statements each (min=median=max=7),
exactly 1.000 grantee lookups each, identical in both index states.** With the
index absent those refusals alone scan the whole table 6,000 times — 3.4 M
buffer hits, ~26 GiB of page traffic, to say no.

Per-API: with the index absent, **29 of 29 read operations issue the sequential
scan**; only `POST /oauth/tokens` does not. With it present there is not a
single Seq Scan anywhere on the surface.

## The two faults, both found by ignoring the summary line

**The classifier only knew 13 of the 29 ops.** `operation_templates` defaulted
to `api_sweep.read_operations`, frozen at 13. Every authorised-tier capture left
16 ops unclassified, and an unclassified request keeps its raw path as its
label — `GET  /policies` became 200 one-request "ops" named after individual
catalogs while its own template row read zero.

Reconciliation missed it **because the two errors net out**: 75 requests missing
from template rows, 77 arriving on raw-path rows, sum +2 — exactly what the
liveness probe costs. Every one of the six captures reported a normal-looking
total. It only showed in the per-row composition. It had also mis-filed 1,600
authz and 75 admin requests into `unclassified (not an op)`, the bucket whose
entire job is keeping non-API traffic out of the permitted mean.

The sentinels for the full surface were already in `_SENTINELS` with a comment
saying they were there for `full_read_operations`. The default was simply never
switched. A prepared fix nobody finished is indistinguishable from no fix.

**The liveness probe's +2 was reported as unexplained.** `assert_capture_live`
authenticates once and reads one catalog before each drive; neither is in the
run manifest. So all six reconciled at +2 and printed "is not what the drive
issued" — false, and a banner that cries wolf every run teaches you to skip the
one check that catches a genuinely short capture. Now named per label, capped at
the probe's own cost, never applied to a negative delta.

## Wrong turns

- **The HANDOFF said nothing had been EXPLAINed. Six qprofile JSONs with full
  plans were already on disk**, taken 11:17-11:18 that morning. Acting on the
  document would have meant re-running the sweep and toggling the index twice
  for data that already existed. Check content before trusting a document about
  content — the same rule this repo already has for capture directories, applied
  to its own handoff.
- **Relabelling could not go through `profile_queries.py`.** Re-running it
  without `--explain` would have overwritten the plans with nothing, and half of
  them were taken in a cluster state that no longer exists. Hence
  `relabel_capture.py` writing a separate `relabel-*.json`: the qprofile is the
  EXPLAIN record, the relabel file is the label record.
- **`prelude_by_outcome` returns sets**, which `json.dumps` refuses. Caught on
  the write, so no file was corrupted — but four files had already been
  regenerated by the time it raised on the fifth.

## Not explained, and left visible

The index-absent passes issued **more statements**, not just slower ones:
122,010 vs 109,010 on the user tier, concentrated in `GET  /namespaces` (13.5 vs
8.0 per request). An index changes how a statement executes, never how many are
issued, so this is something else — most plausibly Polaris entity-cache warmth,
since the absent passes ran first. Consequence: **statement counts are not
comparable across the two halves**, and part of the elapsed-time drop is fewer
statements rather than faster ones. Recorded as unexplained rather than
attributed.
