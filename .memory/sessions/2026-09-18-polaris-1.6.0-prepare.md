# 2026-09-18 — preparing the Polaris 1.6.0 upgrade, and three things the handoff had wrong

Cowork session. No cluster reach: no `kubectl`, `helm`, `psql`. Task was to read CLAUDE.md,
MEMORY.md and `polaris/HANDOFF-upgrade-1.6.0-2026-09-17.md`, prepare the upgrade, set the log
threshold to INFO rather than DEBUG, and commit.

## What Kade decided

- **Console log threshold INFO, not DEBUG.** Stated up front, not derived.
- Asked, and answered: **demote the DEBUG categories too** rather than leave them annotated,
  and **switch the configmap to the plural `polaris.event-listener.types`** rather than file
  the deprecation as a separate issue.

## The wrong turn I did not take

The obvious move was to bump `image.tag` to `1.6.0-incubating`, mirroring 1.3.0. That is
wrong — Polaris graduated from the incubator after 1.3.0, and upstream's 1.6.0 chart pins
`tag: "1.6.0"`. Reading the upstream chart at the tag caught it; copying the existing line's
shape would not have.

## The three corrections

The handoff was written to be read cold and was mostly right about *order*. It was wrong about
the risk.

1. **Schema v5 is not this upgrade's problem.** The handoff's headline risk was the v5
   migration altering `events.catalog_id` — the table the audit event listener writes. But
   `DatabaseType.java` at `apache-polaris-1.6.0` declares latest schema version **4**. v5 is
   1.7.0. Upstream's own note that the `__realm__` placeholder v5 cleans up "only ever
   existed in 1.6.0 release candidates" corroborates it.
2. **v3 → v4 is additive only.** I compared the two scripts object by object rather than
   trusting v4's header comment — which is just as well, because that header says only
   "Changes from v2: added `events`, `idempotency_records`" and never mentions the two
   metrics-report tables or the three new indexes it also adds. Every shared table is
   identical. So the migration is 11 new objects and a version bump, all `IF NOT EXISTS`,
   which means applying the shipped `schema-v4.sql` to a v3 database *is* the migration.
3. **`maxReplicas 3 → 1` was not in the working tree.** The handoff asserted it was, twice,
   and built its remedy C on top of that. `git diff` showed exactly one uncommitted hunk:
   `logging.console.threshold: DEBUG → INFO`. `#8` is still armed. This is the second time in
   this repo that a document asserted a config state that was never there — the same shape as
   `#F1` and the `postgresql:` nesting, just in prose instead of YAML.

## The thing nobody had written down

1.6.0 **tightened entity-name validation**: control characters, dots, backslashes, colons and
similar are rejected, and existing entities carrying them must be renamed *before* upgrading.
Catalogs and namespaces here come from test ladders. That is the only part of this upgrade
that can require a data change before it can proceed, and it was absent from the handoff. It
is now step 1 of the runbook, with the caveat that my screen query was written from upstream's
prose and not from 1.6.0's validation code.

## The INFO decision has a consequence worth stating

Quarkus applies the stricter of the category level and the handler level. With
`console.threshold: INFO`, the ten `DEBUG` categories in `polaris/values.yaml` — auth,
catalog, admin, `core.persistence`, `core.storage`, `service.storage`, `DatasourceOperations`
— emit nothing. Plus three `io.polaris.*` legacy aliases that were doubly dead: the packages
no longer exist *and* the handler would have filtered them anyway.

Leaving thirteen DEBUG lines that cannot fire is precisely the inert-configuration trap this
repo has been burned by. So they are all INFO now, and the `categories:` comment records the
old set and the `helm --set` incantation to bring it back for one run of the `#15` ladder.
`#15` and `#24` were both characterised with that detail on; re-running either without the
override will read as "quieter", not as "fixed".

## Not done, deliberately

Polaris's runtime shape. `replicaCount`, `autoscaling`, persistence, auth, realms, the event
listener type, the shared log PVC — all untouched. *Polaris is not to be changed* still holds;
this is a version bump plus one logging decision. `#8` and the two pgpool remedies from the
handoff stay open as separate decisions.

## State at the end

Committed, unverified: values, chart, configmap template, `migrate_v3_to_v4.sql`,
`polaris/RUNBOOK-upgrade-1.6.0.md`. Nothing rendered, nothing linted, nothing applied. The
cluster runs 1.3.0-incubating with DEBUG console output, and will until Kade runs steps 0–5.

## Step 0, run by Kade — and #5 turned out to be false

`helm get values benchmarks-polaris` finally ran, 15 days after `#5` was filed on the premise
that it would show the file and the cluster disagreeing. Flattened and diffed, the working tree
matched the live release on **all 210 keys** except the 14 `afc88e2` changed, and `--all` added
nothing over the supplied values, so there was no chart-default layer either. **`#5` is
refuted, not merely narrowed.**

That is the third file this issue has named and the third to reconcile. The lesson is not "the
repo is fine" — it is that *"the file is probably wrong"* is itself a claim that needs evidence,
and here it never had any beyond one ambiguous reading.

### My own wrong turn, one turn deep

Between the ConfigMap grep and the values capture I wrote that `console.level=INFO` running
against a committed `DEBUG` was "`#5` caught in the act". It was not. The **working tree** said
INFO; only `HEAD` lagged, by a single uncommitted edit Kade had already applied at revision 5.
I had the ConfigMap and inferred divergence from it before the comparison that could test the
inference existed. Retracted in `#33` in place rather than quietly edited, because the retraction
is the more useful record.

### The inert config was somewhere else entirely

Two real instances, both found in the capture I nearly did not need:

1. **The console emits JSON.** `extraEnv` sets `QUARKUS_LOG_CONSOLE_JSON_ENABLED=true`.
   Environment variables sit at SmallRye ordinal 300, `application.properties` at 250, so the
   env var wins and `logging.console.json: false` plus the entire `logging.console.format`
   string are dead. The ConfigMap renders that format faithfully and Polaris ignores it. The
   tier-2 Lua and report schema v6 parse the JSON, so the pipeline's real dependency is an
   `extraEnv` entry, not the two values keys that look like they govern it.

2. **`topologySpreadConstraints` selects `app.kubernetes.io/name: polaris`** — which matches
   zero pods, because the chart labels them `benchmarks-polaris`. The constraint has never
   influenced scheduling. This is the *same* mistake I made writing the runbook's selector, and
   `#8`'s own argument leans on the `ScheduleAnyway` spreading it is supposed to provide.

Neither is a threshold. Both were found by reading the capture rather than the file.

### One risk raised and closed with evidence

`extraEnv` sets `-XX:+UseZGC -XX:+ZGenerational`. That flag was introduced in JDK 21,
deprecated in 23, obsolete in 24 and **removed in 25** — on a JDK 25 base image it is an
unrecognized VM option and the JVM refuses to start, which surfaces as CrashLoopBackOff with
nothing useful in the Polaris log. Checked: 1.6.0's `Dockerfile.jvm` pins
`registry.access.redhat.com/ubi9/openjdk-21-runtime`, so the flag stays valid. Recorded as a
forward watch item rather than dropped, because the failure mode is silent and severe.

### What the capture said about #15 and #8

- **Hypothesis C is dead.** One pod. No second entity cache to diverge from.
- **Hypothesis A got stronger.** `QUARKUS_DATASOURCE_JDBC_MAX_SIZE=300` per pod means a write
  and the read that follows it are almost certainly on different Agroal connections, so
  pgpool's `disable_load_balance_on_write = always` — session-scoped — cannot cover the
  create-then-resolve path. With `delay_threshold` unset, lag is never consulted. The handoff's
  remedy A addresses precisely this.
- **`#8` is re-armed**, its 2026-09-09 "no metrics, cannot scale" reading superseded, and its
  reasoning partly undercut by the inert spread constraint.

### Still not done

Step 1, the entity-name screen — the only remaining pre-flight that can block the upgrade.
Nothing has been applied; the cluster runs 1.3.0-incubating.
