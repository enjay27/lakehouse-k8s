# Admin / Teardown Utilities

## Concept
Operational maintenance notebooks for resetting a Polaris instance to a clean slate — distinct from the assertion-style test suites in the other directories.

## Purpose
Provide a safe, ordered teardown that drops all tables/views, namespaces, catalogs, principals, principal roles, and catalog roles, so a test environment can be reset between runs.

## Notebooks
- `polaris_clean_all.ipynb` — previews everything that will be deleted, then deletes in dependency order (enables `drop-with-purge.enabled=true` first so drops aren't blocked by the config gate).
- `polaris_reset_principal.ipynb` — **scoped** reset (not a full wipe): deletes one principal, its `{PRINCIPAL_NAME}_role` principal-role, and the non-default catalog-roles on `my_{PRINCIPAL_NAME}_catalog`. Built on `src/polaris_rest.PolarisREST` (the shared REST client — its first notebook adopter) rather than hand-rolled `requests` calls. GETs each resource first (steps 1–4), deletes (steps 5–7), then re-GETs everything to verify it's gone (step 8). **The catalog itself is left in place by design** — only the principal/role wiring on it is removed. Set `PRINCIPAL_NAME` in the parameters cell before running; safe to re-run (idempotent — already-deleted resources just show as not-found).
- `polaris_rotate_credential.ipynb` — **⚠️ deprecated**, kept for historical record. Finds who holds a given principal-role and attempts to rotate that principal's OAuth credentials as root; stops at an unresolved 403 (`/rotate` is self-service only) and a 404 (no privilege exists to grant root around it). Superseded by `polaris_rotate_principal.ipynb` below.
- `polaris_rotate_principal.ipynb` — rotates one principal's OAuth credentials **without deleting anything** (unlike `polaris_reset_principal.ipynb`, the principal, its principal-role assignment, and its catalog-roles all survive untouched). Built on `src/polaris_rest.PolarisREST`'s `reset_principal_credentials`/`rotate_credentials` methods. Documents, as deliberate negative-result cells, exactly why the naive approach fails: root's self-service `/rotate` attempt on another principal 403s by design, granting `PRINCIPAL_ROTATE_CREDENTIALS` to `service_admin` 404s because Principal isn't a securable object in Polaris's RBAC model at all, and an OAuth impersonation/token-exchange workaround is infeasible (no such grant type exists, and root can't read an existing principal's secret to fake one). Then completes the actual rotation via the admin-callable `POST /principals/{name}/reset` endpoint (Polaris 1.2+, gated by the `ENABLE_CREDENTIAL_RESET` feature flag, default on) followed by a self-service `/rotate` demo using the reset credentials. Set `PRINCIPAL_NAME` in the parameters cell before running; **not idempotent** — every run issues fresh credentials and invalidates the previous pair.
- `polaris_rotate_principal_test.ipynb` — **live test harness** for the notebook above. `polaris_rotate_principal.ipynb` expects an existing `PRINCIPAL_NAME`; this one generates its own — it provisions a throwaway `rotate-test-<unix-timestamp>` principal WITH real role wiring (a principal-role, a dedicated catalog, a catalog-role, and an actual `CATALOG_MANAGE_CONTENT` grant), runs it through the identical 403 → 404 → impersonation-ruled-out → `/reset` → verify → `/rotate` → verify flow, additionally proving the grant (not just the login) survives rotation by listing namespaces with the final credentials, then tears everything down and sweeps any `rotate-test-*` leftovers from a previous crashed run. No parameters to set; safe to re-run repeatedly (unique name per run, idempotent teardown/sweep). Includes a live-measured correction (2026-07-08): a credential superseded by ONE `/rotate` call still authenticates (Polaris keeps it as a "secondary" secret) — full eviction takes a second rotation, asserted and proven in a dedicated cell.
- `polaris_reset_vs_rotate_test.ipynb` — **focused, detailed test** of exactly when a superseded secret stops working under each API — prompted by a live run where `/reset`-issued credentials were found to invalidate immediately, unlike `/rotate`. Provisions a minimal throwaway principal (no catalog — role-wiring survival is already covered by the notebook above), then asserts: `/rotate` (self-service) needs **two** calls to fully evict a secret (one call only demotes it to a still-valid "secondary" secret); `/reset` (root) needs **just one** (it double-rotates internally, confirmed via a bonus second-reset check that this holds across generations, not just at creation time). Ends with a side-by-side summary printout, teardown, and a `reset-vs-rotate-*` sweep. No parameters to set.

## How to run
1. **Read the preview / GET-step cell output before proceeding** — these notebooks are destructive (or, for the rotate/reset notebooks, credential-invalidating).
2. **Restart & Run All** only against an environment you intend to modify. For `polaris_reset_principal.ipynb` and `polaris_rotate_principal.ipynb`, set `PRINCIPAL_NAME` first — the two `*_test.ipynb` notebooks need no parameters.

## ⚠️ Scope & safety — LOCAL DEVICE ONLY (do NOT refactor onto shared config)
Every notebook in this directory is intentionally **hardcoded to the local device** (`POLARIS_URL=http://192.168.139.2:8181`, local `client_secret`), with a host-guard `assert`. This is **deliberate, not a gap**:

- They are **never** run against the company DEV or PROD environment. They exist purely to reset/manage the local OrbStack instance.
- `polaris_clean_all.ipynb` is **fully destructive**: it deletes *all* catalogs, namespaces, principals, and roles. `polaris_reset_principal.ipynb` is destructive but scoped to one named principal. In a shared environment either would risk **other users' data**.
- They must therefore **not** be wired to `init_env()` / `src/config/`. Hardcoding to localhost is a safety feature — it cannot be repointed at a shared cluster by switching an env file.

**Before running, confirm the target host is your local device. Never change the URL to a DEV/PROD host.**
